## Nomenclatura de rutas — URLs RESTful (sección 6, pág. 4-5)

Lineamientos generales, textuales (pág. 4):

- "Una URL identifica un recurso."
- "Las URLs DEBEN incluir sustantivos, no verbos."
- "Usar sustantivos en plural solamente para consistencia (no sustantivos en singular)."
- "Usar los verbos HTTP apropiados (*GET, POST, PUT, PATCH, DELETE*) para operar en las
  colecciones y elementos."
- **Profundidad máxima de anidamiento**: "No se debe necesitar ir más allá de
  resource/identifier/resource."
- "Especificar campos opcionales como una lista separada por coma."
- **Formato de respuesta por header, JSON por defecto**: "Para indicar el formato de respuesta,
  utilizar el campo *content-type* del header siendo por defecto el formato JSON. Por ejemplo:
  XML: `Content-Type: application/xml` / JSON: `Content-Type: application/json; charset=utf-8`"
- **Patrón de ruta**: "El formato puede ser: `api/v2/resource/{id}`"

Ejemplos válidos de URLs (pág. 5), textuales:

- Obtener la lista de artículos: `GET http://www.buenosaires.gob/api/v1/articulos`
- Filtrar con query string: `GET http://www.buenosaires.gob/api/v1/articulos?year=2016&sort=desc`
- Obtener un artículo en formato JSON: `GET http://www.buenosaires.gob.ar/api/v1/articulos/1234`
- Agregar un comentario a un artículo específico: `POST http://www.buenosaires.gob.ar/api/v1/articulos/1234/comentarios`

Ejemplos NO válidos de URLs (pág. 5), textuales:

- Sustantivos singulares: `http://www.buenosaires.gob.ar/articulo`
- Filtro fuera del query string: `http://www.buenosaires.gob/articulos/2016/desc`
- Formato de número de versión: `GET http://www.buenosaires.gob.ar/api/v1/articulos/1234`
  — **atención: esta URL figura además como ejemplo válido en la misma página.** Ver
  "Contradicciones internas".

## Soporte JSON (sección 8, pág. 5-6)

- **La respuesta debe ser un objeto, no un array** (pág. 5) — "Las respuestas DEBEN ser un
  objeto JSON (no un array): usar un array para retornar resultados limita la capacidad de
  incluir metadata sobre resultados y la capacidad de las API's para agregar *top-level keys*
  en el futuro."
- **Claves predecibles** (pág. 5) — "No usar claves impredecibles: realizar el parsing de una
  respuesta JSON donde las claves son impredecibles es difícil y genera malestar a los
  clientes."
- **Convención de nombres de claves** (pág. 5) — "Usar *guión_bajo* para las claves: diferentes
  lenguajes usan diferentes convenciones. JSON usa *guión_bajo*, no *camelCase*."
  (Varias claves de los ejemplos JSON del propio documento usan camelCase —`developerMessage`,
  `userMessage`, `errorCode`, `moreInfo` (pág. 6-7), `userId` y `postId` (pág. 10)—, mientras que
  otros ejemplos no tienen ninguna clave camelCase: `tags`/`id`/`name` (pág. 6) y
  `metadata`/`resultset`/`count`/`offset`/`limit` (pág. 9). Ver "Contradicciones internas".)
- **Nota editorial sin resolver en el documento** (pág. 5): el texto dice literalmente "Rever
  estándar Json**", con dos asteriscos y sin nota al pie asociada. No hay estándar JSON
  adicional referenciado, solo "Más info en json.org".
- **Respuestas** (pág. 6) — "No incluir valores en las claves." y "La metadata solamente debe
  contener propiedades directas a la respuesta, no propiedades relacionadas a la información
  de la respuesta."
- Ejemplo válido (pág. 6): `"tags": [ {"id": "125", "name": "Ciudadano"}, {"id": "834", "name": "Servicios"} ],`
- Ejemplo NO válido (pág. 6): `"tags": [ {"125": "Ciudadano"}, {"834": "Servicios"} ],`

## Versionado de la documentación de API (sección 12, pág. 9)

- "Los números de versión deben abarcar tres niveles de versión: X.Y.Z"

## Seguridad de transporte (sección 15, pág. 11)

- **HTTPS obligatorio** (pág. 11) — "Cualquier API que se desarrolle debe usar HTTPS encryption
  (TLS/SSL)."
- **Configuración exigida** (pág. 11) — "HTTPS debe estar configurado aplicando las mejores
  prácticas, incluyendo cifrado que soporte *forward secrecy* y Seguridad de transporte HTTP
  estricta (*HTTP Strict Transport Security*)."
- **CORS sobre HTTPS** (pág. 11) — "Para solicitudes CORS a la API para trabajar en los sitios
  web HTTPS - para no ser bloqueado en forma de contenido mixto - esas peticiones deben ser a
  través de HTTPS."
- **Migración de APIs existentes** (pág. 11) — "Para APIs existentes que corren sobre HTTP, el
  primer paso es agregar soporte HTTPS y actualizar la documentación aclarando que es la
  configuración por defecto, usándolo en los ejemplos, etc. Luego, evaluar la posibilidad de
  deshabilitar o redireccionar a peticiones HTTP." (Para lo existente el corte de HTTP queda
  como evaluación, no como obligación.)

## CORS (sección 17, pág. 12)

- **CORS obligatorio** (pág. 12) — "Para que los clientes puedan usar una API desde el front de
  una aplicación, la API DEBE tener habilitado CORS."
- **Caso simple** (pág. 12) — "Para el más simple y común caso de uso, donde toda la API entera
  deba ser accesible desde el navegador, habilitar CORS es tan simple como incluir esta cabecera
  HTTP en todas las respuestas:" y lista, sin distinguir cuál corresponde a cuál caso:
  `Access-Control-Allow-Origin: *` · `Access-Control-Allow-Origin: http://example.com` ·
  `Access-Control-Allow-Methods: PUT, POST, DELETE`
- **Cabeceras y su significado** (pág. 12), textual: `Access-Control-Allow-Origin` "¿qué origen
  está permitido?" · `Access-Control-Allow-Credentials` "¿también se aceptan solicitudes cuando
  el modo de credenciales es incluir (include)?" · `Access-Control-Allow-Headers` "¿qué cabeceras
  pueden utilizarse?" · `Access-Control-Allow-Methods` "¿qué métodos de petición HTTP están
  permitidos?" · `Access-Control-Expose-Headers` "¿qué cabeceras pueden mostrarse?" ·
  `Access-Control-Max-Age` "¿cuándo pierde su validez la solicitud preflight?" ·
  `Access-Control-Request-Headers` "¿qué header HTTP se indica en la solicitud preflight?" ·
  `Access-Control-Request-Method` "¿qué método de petición HTTP se indica en la solicitud
  preflight?"
- **Restricción de uso** (pág. 12) — "se corre el riesgo de que los administradores web se
  aprovechen de las wildcards por comodidad, haciendo que la protección de la SOP sea en vano.
  Por eso, es importante utilizar el CORS solo en casos especiales y configurarlo de la manera
  más restrictiva posible."

## Contradicciones internas

1. **La misma URL figura como ejemplo válido y como ejemplo NO válido (pág. 5).**
   - Lado A, "Ejemplos válidos de URLs — Obtener un artículo en formato JSON":
     `GET http://www.buenosaires.gob.ar/api/v1/articulos/1234`
   - Lado B, "Ejemplos NO válidos de URLs — Formato de número de versión":
     `GET http://www.buenosaires.gob.ar/api/v1/articulos/1234`
   - Ambos en la pág. 5, con doce líneas de distancia. El documento no explica qué tiene de
     mal el formato de versión en el lado B. **No resolver por cuenta propia: consultar.**

2. **camelCase vs guión_bajo en las claves JSON (pág. 5 contra pág. 6-7 y 10).**
   - Lado A (regla, pág. 5): "Usar *guión_bajo* para las claves: diferentes lenguajes usan
     diferentes convenciones. JSON usa *guión_bajo*, no *camelCase*."
   - Lado B (ejemplos del propio documento): el cuerpo del error usa `developerMessage`,
     `userMessage`, `errorCode`, `moreInfo` (pág. 6-7) y los ejemplos de respuesta usan
     `userId` (pág. 10) y `postId` (pág. 10) — todos camelCase.
   - Es decir: **el formato del error exigido en la sección 10 viola la convención de claves
     exigida en la sección 8.**

3. **"3 simples códigos de respuesta" vs el listado completo y lo que hay que documentar.**
   - Lado A (pág. 7): "Usar estos 3 simples códigos de respuesta... 200 - OK / 400 - Bad
     Request / 500 - Internal Server Error".
   - Lado B (pág. 7-8): la sección 10.1 publica ~60 códigos de estado sin marcarlos como
     prohibidos ni como excepcionales; y la sección 18 exige documentar "posibles códigos de
     estado (200, 400, 401, etc.)" (pág. 13), donde 401 no está entre los tres.

4. **Versionado: "números enteros, no decimales" vs los ejemplos de tres niveles (pág. 9).**
   - Lado A: "Las versiones deben ser expresadas en números enteros, no decimales, con el
     prefijo 'v'." y "Los números... se incrementan en 1, **comenzando en 1**."
   - Lado B, en la misma página: "Válido: v1.0.0, v2.1.0, v3.5.0" — formato de tres niveles
     con componentes en `0`, incompatible con "comenzando en 1"; y "v1.0.0" difícilmente sea
     "número entero, no decimal".

5. **CORS permisivo vs CORS restrictivo (pág. 12).**
   - Lado A: "habilitar CORS es tan simple como incluir esta cabecera HTTP en todas las
     respuestas: `Access-Control-Allow-Origin: *`".
   - Lado B, cierre de la misma sección: "es importante utilizar el CORS solo en casos
     especiales y configurarlo de la manera más restrictiva posible."

6. **Título del documento inconsistente (menor).**
   - Portada (pág. 1): "ES0903 - Estándar de Desarrollo API".
   - Pie de página de todas las páginas (pág. 3-14): "ES0903 - Estándar de Desarrollo de APIs".
