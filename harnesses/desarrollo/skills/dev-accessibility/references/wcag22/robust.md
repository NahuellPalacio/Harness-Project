# Principle 4: Robust

> Content must be robust enough that it can be interpreted by a wide variety of user agents, including assistive technologies.

Source of normative text: W3C Recommendation *Web Content Accessibility Guidelines (WCAG) 2.2*, 12 December 2024, https://www.w3.org/TR/WCAG22/. Blockquotes under "Normative text (verbatim)" are copied from the Recommendation. Sections labeled *informative* are practice guidance and do not create requirements.

Key glossary terms (short forms; full definitions in `glossary.md`):

- **name** — text by which software can identify a component within web content to the user. May be hidden and only exposed by assistive technology (unlike a *label*, which is presented to all users). Unrelated to the HTML `name` attribute.
- **role** — text or number by which software can identify the function of a component within Web content (e.g., whether an image functions as a hyperlink, command button, or check box).
- **state** — dynamic property expressing characteristics of a user interface component that may change in response to user action or automated processes (focus, hover, select, press, check, visited/unvisited, expand/collapse).
- **user interface component** — a part of the content that is perceived by users as a single control for a distinct function; includes form elements, links and components generated by scripts.
- **programmatically determined** — determined by software from author-supplied data in a way that different user agents, including assistive technologies, can extract and present to users in different modalities.
- **programmatically set** — set by software using methods that are supported by user agents, including assistive technologies.
- **status message** — change in content that is not a change of context, and that provides information to the user on the success or results of an action, on the waiting state of an application, on the progress of a process, or on the existence of errors.
- **assistive technology** — hardware and/or software that acts as a user agent, or along with a mainstream user agent, to provide functionality to meet the requirements of users with disabilities beyond those offered by mainstream user agents (screen readers, magnifiers, speech recognition, alternative keyboards and pointing devices).
- **accessibility supported** — supported by users' assistive technologies as well as the accessibility features in browsers and other user agents (a precondition for relying on any technique; see Conformance Requirement 4).

## Guideline 4.1 Compatible

> Maximize compatibility with current and future user agents, including assistive technologies.

### 4.1.1 Parsing (Obsolete and removed)

**Normative text (verbatim):**

> NOTE
>
> This criterion was originally adopted to address problems that assistive technology had directly parsing HTML. Assistive technology no longer has any need to directly parse HTML. Consequently, these problems either no longer exist or are addressed by other criteria. This criterion no longer has utility and is removed.

The WCAG 2.2 Recommendation also states, in its introduction (verbatim): "WCAG 2.2 has removed one success criterion, 4.1.1 Parsing. Authors that are required by policy to conform with WCAG 2.0 or 2.1 will be able to update content to WCAG 2.2, but may need to continue to test and report 4.1.1."

**What this means for audits (informative):**
- Under **WCAG 2.2**, 4.1.1 has no requirements. Do not report parsing/validation issues against 4.1.1. In a 2.2 report, list it as "Not applicable — removed in WCAG 2.2".
- Under **WCAG 2.0 / 2.1** (when a policy, contract or law still cites those versions — e.g., EN 301 549 editions or national regulations), the W3C's current Understanding guidance (errata to 2.0 and 2.1) is that 4.1.1 should be considered always satisfied for any content using HTML or XML, because user agents repair parse errors before exposing content to assistive technology. The original 2.1 text (for reference) required that elements have complete start and end tags, are nested according to their specifications, do not contain duplicate attributes, and that IDs are unique, except where the specification allows these features. The *only* historical 4.1.1 problems that still affect users — duplicate `id` values that break `label for`, `aria-labelledby`, `aria-describedby`, `aria-controls` or `headers` references, and malformed nesting that breaks the accessibility tree — are now reported under **1.3.1 Info and Relationships** or **4.1.2 Name, Role, Value**, where the user impact actually occurs.
- Recommended reporting line for mixed-version reports: "4.1.1 Parsing — Satisfied (WCAG 2.0/2.1, per W3C errata); removed in WCAG 2.2. Markup issues with user impact are reported under 1.3.1 and 4.1.2."

**How to test (if a 2.0/2.1 report is required):**
1. Run an HTML validator or DOM check for duplicate `id` attributes and broken nesting (e.g., interactive content nested inside interactive content, `<div>` inside `<p>`, unclosed elements that cause re-parenting).
2. For each finding, check whether it is referenced by an association attribute or changes the accessibility tree. If so, record the defect under 1.3.1 or 4.1.2 with its actual effect (wrong label, missing name, wrong structure). If not, note it as a code-quality observation only.

**Sufficient techniques:** None listed in the WCAG 2.2 Quick Reference (the criterion is removed).

**Related:** 1.3.1 Info and Relationships, 4.1.2 Name, Role, Value.

### 4.1.2 Name, Role, Value (Level A)

**Normative text (verbatim):**

> For all user interface components (including but not limited to: form elements, links and components generated by scripts), the name and role can be programmatically determined; states, properties, and values that can be set by the user can be programmatically set; and notification of changes to these items is available to user agents, including assistive technologies.
>
> NOTE
>
> This success criterion is primarily for web authors who develop or script their own user interface components. For example, standard HTML controls already meet this success criterion when used according to specification.

**Intent (informative):** Assistive technologies (screen readers, voice control, switch access) work through the platform accessibility API. For every control they need to know *what it is* (role), *what it is called* (name), *what state or value it has* (checked, expanded, selected, pressed, disabled, current value) and to be *told when that changes*. Native HTML elements (`<button>`, `<a href>`, `<input>`, `<select>`, `<details>`, `<dialog>`) provide all of this for free. Custom components built from `<div>`/`<span>` and script provide none of it unless the author adds WAI-ARIA roles, states and properties and manages focus and keyboard interaction. Missing names make controls unusable by voice-control users ("click Buscar" has nothing to match) and screen-reader users ("button" with no label). Missing roles make a clickable `<div>` invisible as a control. Missing state updates leave users unaware that a menu opened or a checkbox toggled.

**How to test:**
1. Enumerate all user interface components, including custom widgets (dropdowns, tabs, accordions, toggles, sliders, date pickers, carousels, modal dialogs, menus, tree views, data grids, chat widgets, map controls, embedded iframes).
2. For each component, inspect the browser's accessibility tree (DevTools → Accessibility pane) or use an inspector (axe, Accessibility Insights, ARC) and confirm:
   - **Role** is exposed and correct for what the component does (a thing that acts like a button is exposed as `button`, not `generic`/`text`; a link that navigates is `link`; a toggle is `checkbox`/`switch`/`button` with `aria-pressed`).
   - **Name** is exposed and non-empty, and describes the purpose (see Appendix A for the computation order). Icon-only buttons, image links, search fields, close "×" buttons and iframes are the usual gaps.
   - **States/properties/values** that the user can change are exposed and current: `aria-expanded`, `aria-checked`/`aria-pressed`/`aria-selected`, `aria-disabled`/`disabled`, `aria-valuenow/min/max/text`, `aria-current`, `aria-invalid`, `aria-haspopup`, `aria-controls`, selected option in listbox/combobox.
   - **Notification of changes**: after operating the component (keyboard and pointer), the state in the accessibility tree updates (e.g., `aria-expanded` flips, `aria-checked` toggles, slider value changes) and a screen reader announces the change.
3. Run a screen reader (NVDA/JAWS on Windows, VoiceOver on macOS/iOS, TalkBack on Android) through the components in both browse and focus/forms mode; every control should announce role, name and state on focus and announce state changes on operation.
4. Check ARIA validity: roles exist in the ARIA spec, required owned elements/properties are present (`role="tab"` inside `role="tablist"`, `aria-controls` targets exist, `aria-labelledby` IDs exist and are unique), no prohibited attributes for the role, no conflicting native + ARIA semantics.
5. Pass: every component exposes correct role, non-empty descriptive name, current states/values and change notifications. Fail: any control missing a name or role, a state that does not update, or an ARIA relationship pointing to a missing/duplicate ID.

**Common failures:**
- F59 Failure of Success Criterion 4.1.2 due to using script to make div or span a user interface control in HTML without providing a role for the control
- F15 Failure of Success Criterion 4.1.2 due to implementing custom controls that do not use an accessibility API for the technology, or do so incompletely
- F20 Failure of Success Criterion 1.1.1 and 4.1.2 due to not updating text alternatives when changes to non-text content occur
- F42 Failure of Success Criteria 1.3.1, 2.1.1, 2.1.3, or 4.1.2 when emulating links
- F68 Failure of Success Criterion 4.1.2 due to a user interface control not having a programmatically determined name
- F79 Failure of Success Criterion 4.1.2 due to the focus state of a user interface component not being programmatically determinable or no notification of change of focus state available
- F86 Failure of Success Criterion 4.1.2 due to not providing names for each part of a multi-part form field, such as a US telephone number
- F89 Failure of Success Criteria 2.4.4, 2.4.9 and 4.1.2 due to not providing an accessible name for an image which is the only content in a link
- F111 Failure of Success Criteria 1.3.1, 2.5.3, and 4.1.2 due to a control with visible label text but no accessible name
- Typical (informative): `<div onclick>` hamburger menu with no role/name/`tabindex`; a "×" close button whose name is "times"; an accordion header whose `aria-expanded` never changes; a `<a href="#">` used as a button; a custom select with `role="listbox"` but no `aria-selected`; a "favourite" star toggle with no `aria-pressed`; an `<iframe>` with no `title`; an `<input>` with a placeholder but no label.

**Sufficient techniques:**
- Situation A: If using a standard user interface component in a markup language (e.g., HTML):
  - ARIA14 Using aria-label to provide an accessible name where a visible label cannot be used
  - ARIA16 Using aria-labelledby to provide a name for user interface controls
  - G108 Using markup features to expose the name and role, allow user-settable properties to be directly set, and provide notification of changes — using one or more of: H91 Using HTML form controls and links; H44 Using label elements to associate text labels with form controls; H64 Using the title attribute of the iframe element; H65 Using the title attribute to identify form controls when the label element cannot be used; H88 Using HTML according to spec
- Situation B: If using script or code to re-purpose a standard user interface component in a markup language:
  - Exposing the names and roles, allowing user-settable properties to be directly set, and providing notification of changes — using: ARIA16 Using aria-labelledby to provide a name for user interface controls
- Situation C: If using a standard user interface component in a programming technology:
  - G135 Using the accessibility API features of a technology to expose names and roles, to allow user-settable properties to be directly set, and to provide notification of changes — using one or more of: PDF10 Providing labels for interactive form controls in PDF documents; PDF12 Providing name, role, value information for form fields in PDF documents
- Situation D: If creating your own user interface component in a programming language:
  - G10 Creating components using a technology that supports the accessibility API features of the platforms on which the user agents will be run to expose the names and roles, allow user-settable properties to be directly set, and provide notification of changes — using one or more of: ARIA4 Using a WAI-ARIA role to expose the role of a user interface component; ARIA5 Using WAI-ARIA state and property attributes to expose the state of a user interface component; ARIA16 Using aria-labelledby to provide a name for user interface controls

**Implementation notes (HTML/ARIA/JS):**
```html
<!-- Prefer native elements: name, role, state and keyboard come for free -->
<button type="button" aria-expanded="false" aria-controls="menu">Menú</button>
<ul id="menu" hidden> ... </ul>

<!-- Icon-only control needs a name -->
<button type="button" aria-label="Cerrar">
  <svg aria-hidden="true" focusable="false">…</svg>
</button>

<!-- Toggle state -->
<button type="button" aria-pressed="false">Guardar en favoritos</button>

<!-- Custom checkbox, only if a native one is impossible -->
<div role="checkbox" tabindex="0" aria-checked="false" aria-labelledby="lbl1"></div>
<span id="lbl1">Acepto los términos</span>

<!-- Frame -->
<iframe title="Mapa de la sede" src="…"></iframe>
```
```js
// Keep state in sync with the visual state — this is what provides "notification of changes"
toggle.addEventListener('click', () => {
  const open = toggle.getAttribute('aria-expanded') === 'true';
  toggle.setAttribute('aria-expanded', String(!open));
  menu.hidden = open;
});
```

**Related:** 1.1.1 Non-text Content (names for image controls), 1.3.1 Info and Relationships (labels and structure), 2.1.1 Keyboard (custom controls must also be operable), 2.4.4 / 2.4.9 Link Purpose, 2.5.3 Label in Name, 3.3.2 Labels or Instructions, 4.1.3 Status Messages.

### 4.1.3 Status Messages (Level AA)

**Normative text (verbatim):**

> In content implemented using markup languages, status messages can be programmatically determined through role or properties such that they can be presented to the user by assistive technologies without receiving focus.

**Intent (informative):** When a page shows feedback that does *not* move focus — "3 results found", "Item added to cart", "Saving…", "Form submitted successfully", "5 errors found", a progress indicator — sighted users see it appear, but screen-reader users hear nothing unless the message is exposed through a live region or a status/alert/log/progressbar role. The criterion applies only to *status messages* as defined (a change of content that is not a change of context and that gives information on success/results, waiting state, progress, or errors). It does not apply to messages that receive focus (a modal dialog or an error summary that is focused), to changes of context, or to content that is not a status (e.g., a newly expanded panel). Focusing the message would interrupt the user; the criterion asks for announcement *without* focus.

**How to test:**
1. Identify every status message triggered by user actions or processes: search/filter result counts, "added to cart/basket", save confirmations, "loading"/"please wait", progress bars, inline validation summaries and error counts that appear without focus moving, "copied to clipboard", "connection lost".
2. For each, inspect the DOM: the message container must have an appropriate role or live-region property **present in the DOM before the message text is injected**: `role="status"` (polite), `role="alert"` (assertive, for errors/warnings), `role="log"`, `role="progressbar"` with `aria-valuenow`, or `aria-live="polite|assertive"` (optionally `aria-atomic`, `aria-relevant`).
3. With a screen reader, trigger each message and confirm it is announced automatically while focus stays where it was.
4. Confirm that messages that *do* move focus (modal dialogs, focused error summaries) are handled as such (they are not in scope of this criterion), and that non-status content is not wrongly marked `aria-live="assertive"`.
5. Pass: every status message is exposed via role/property and announced without focus. Fail: visual-only toasts, result counts or progress indicators that AT never reports; a live region added to the DOM at the same time as its text (often not announced); `role="alert"` used for trivial non-urgent content.

**Common failures:**
- F103 Failure of Success Criterion 4.1.3 due to providing status messages that cannot be programmatically determined through role or properties
- Using role="alert" or aria-live="assertive" on content which is not important and time-sensitive (future link)
- Typical (informative): a "Producto agregado al carrito" toast in a plain `<div>`; "Mostrando 12 resultados" updated silently; a spinner with no accessible text; a form that shows "Se encontraron 3 errores" at the top without a live region and without moving focus.

**Sufficient techniques:**
- Situation A: If a status message advises on the success or results of an action, or the state of an application:
  - ARIA22 Using role=status to present status messages — in combination with: G199 Providing success feedback when data is submitted successfully
- Situation B: If a status message conveys a suggestion, or a warning on the existence of an error:
  - ARIA19 Using ARIA role=alert or Live Regions to Identify Errors — in combination with any of: G83 Providing text descriptions to identify required fields that were not completed; G84 Providing a text description when the user provides information that is not in the list of allowed values; G85 Providing a text description when user input falls outside the required format or values; G177 Providing suggested correction text; G194 Providing spell checking and suggestions for text input
- Situation C: If a status message conveys information on the progress of a process:
  - ARIA23 Using role=log to identify sequential information updates
  - ARIA25 Using an ARIA live region to convey the status of a progress bar
  - ARIA22 Using role=status to present status messages — AND G193 Providing help by an assistant in the web page
  - ARIA27 Using ariaNotify to convey the status of a progress bar

**Advisory techniques:**
- Using aria-live regions to support 1.4.13 Content on Hover or Focus (future link)
- Using role="timer" (future link)
- ARIA18 Using aria-alertdialog to Identify Errors
- SCR14 Using scripts to make nonessential alerts optional

**Implementation notes (HTML/ARIA/JS):**
```html
<!-- Live region exists on page load, empty; text is injected later -->
<div id="status" role="status" aria-live="polite" aria-atomic="true"></div>
<div id="errors" role="alert"></div>

<div role="progressbar" aria-labelledby="pb-label" aria-valuemin="0" aria-valuemax="100" aria-valuenow="40">
  <span id="pb-label">Subiendo archivo</span>
</div>
```
```js
function announce(text) {
  const el = document.getElementById('status');
  el.textContent = '';            // clear so identical messages re-announce
  setTimeout(() => { el.textContent = text; }, 50);
}
announce('Se encontraron 12 resultados');
```
Guidelines: use `role="status"` / `aria-live="polite"` for most feedback; reserve `role="alert"` for errors and time-critical warnings; keep messages short; do not put interactive controls inside a live region expecting them to be announced; remove or update stale messages; do not rely on `title` tooltips or visually-hidden text alone (not announced without a live region).

**Related:** 3.3.1 Error Identification, 3.3.3 Error Suggestion, 4.1.2 Name, Role, Value, 2.2.1 Timing Adjustable / 2.2.2 Pause, Stop, Hide (auto-updating content), 1.3.1.

## Appendix A — Accessible name and description computation in practice (informative)

Assistive technologies obtain a control's *name* and *description* through the browser's implementation of the Accessible Name and Description Computation. Knowing the precedence lets you predict (and fix) what a screen reader will say.

**Name — precedence, first non-empty wins:**

1. `aria-labelledby` — concatenation of the text of the referenced elements (in the order of the IDs; may include hidden elements; may reference itself).
2. `aria-label` — the attribute's string (not translated by browsers automatically; not visible, so pair it with 2.5.3 Label in Name).
3. **Native labelling** for the element type:
   - form controls: associated `<label>` (via `for`/`id` or wrapping); `<legend>` names a `<fieldset>`; `<caption>` names a `<table>`; `<figcaption>` names a `<figure>`;
   - `<img>`, `<area>`, `<input type="image">`: `alt`;
   - `<button>`, `<a>`, `<summary>`, headings, cells, options, and most roles that allow "name from content": the element's text content and the names of descendant images/controls;
   - `<iframe>`: `title`; `<svg>`: `<title>` child; `<abbr>`: `title`;
   - `<input type="submit|reset|button">`: `value`.
4. `title` attribute (tooltip) — last resort for a name.
5. `placeholder` (for text inputs) — used by browsers as a fallback name when nothing else exists; never rely on it.

If nothing matches, the name is empty — a failure of 4.1.2 for any interactive component (and of 1.1.1 for informative images).

**Description — precedence:** `aria-describedby` (referenced text) → `aria-description` → `title` (if not already used as the name). Descriptions are announced after the name/role/state and are the right place for format hints and error messages (3.3.1–3.3.3).

**Practical rules:**
- Visible text labels beat ARIA strings: they stay in sync when content is translated or edited, and they satisfy 2.5.3 automatically.
- `aria-label`/`aria-labelledby` **replace** the content as the name; `<button aria-label="Cerrar">Cerrar diálogo</button>` is named "Cerrar". Do not use them to "add" information — use `aria-describedby` for that.
- `aria-label` on a `<div>`/`<span>` with no role is ignored by most AT; put names on elements with a role.
- Hidden text (`visually-hidden` CSS class) inside a button is part of the name; `display:none`/`hidden` text is *not*, except when referenced via `aria-labelledby`.
- Every `id` referenced by `aria-labelledby`, `aria-describedby`, `aria-controls`, `aria-owns`, `aria-activedescendant`, `for` or `headers` must exist and be unique in the document.
- Group names: `<fieldset><legend>` or `role="group"|"radiogroup"` + `aria-labelledby` so that AT announces the group when entering it.

Quick check with DevTools: Elements → Accessibility pane shows *Name*, its source ("From label", "From aria-label"…), *Role*, *Description* and ARIA attributes; empty Name on an interactive node is a defect.

## Appendix B — Required roles, states and properties for common custom widgets (informative)

Use native HTML wherever it exists; the table lists what a *custom* implementation must expose to satisfy 4.1.2 (plus the keyboard behaviour required by 2.1.1, from the WAI-ARIA Authoring Practices patterns).

| Widget | Native element (prefer) | Role(s) if custom | Required states / properties | Keyboard (minimum) |
|---|---|---|---|---|
| Button | `<button>` | `button` | accessible name; `aria-disabled` if disabled; `aria-haspopup` if it opens a menu/dialog | Enter, Space |
| Toggle button | `<button aria-pressed>` | `button` | `aria-pressed="true|false"` updated on toggle | Enter, Space |
| Checkbox | `<input type="checkbox">` | `checkbox` | `aria-checked="true|false|mixed"`; name via `aria-labelledby`/`aria-label` | Space |
| Switch | `<input type="checkbox" role="switch">` | `switch` | `aria-checked="true|false"` | Space (Enter optional) |
| Radio group | `<fieldset><legend>` + `<input type="radio">` | `radiogroup` containing `radio` | group name; `aria-checked` on each radio; roving `tabindex` (one tab stop) | Tab into group; Arrow keys move and select |
| Tabs | — | `tablist` > `tab`; `tabpanel` | `aria-selected` on tabs; `aria-controls` tab→panel; `aria-labelledby` panel→tab; roving `tabindex` | Tab to active tab; Arrow keys switch (auto or with Enter/Space); Home/End |
| Accordion | `<details><summary>` | `button` inside heading (`<h3><button>`) + region | `aria-expanded` on the button; `aria-controls` to the panel; optionally `region` with `aria-labelledby` | Enter, Space toggle |
| Disclosure (show/hide) | `<details>` | `button` | `aria-expanded`; `aria-controls` | Enter, Space |
| Menu button + menu | — | `button` with `aria-haspopup="true"`/`"menu"` + `aria-expanded`; `menu` > `menuitem` / `menuitemcheckbox` / `menuitemradio` | `aria-expanded` on the button; `aria-checked` on checkable items; focus management into the menu | Enter/Space/ArrowDown open; Arrows move; Esc closes and returns focus; Home/End; type-ahead |
| Navigation menu (site nav) | `<nav><ul><li><a>` | *not* `menu` (that is for application menus); use lists + links; `aria-expanded` on sub-menu toggles | `aria-current="page"` on the current link | Tab/Shift+Tab; Enter |
| Combobox (autocomplete) | `<input list>` / `<select>` | `combobox` + `listbox` (or `grid`/`tree`) popup | `aria-expanded`, `aria-controls`, `aria-autocomplete`, `aria-activedescendant` (or focus moves to options), `aria-selected` on options; name on the input | Arrows move through options; Enter selects; Esc closes; typing filters |
| Listbox (single/multi select) | `<select>` / `<select multiple>` | `listbox` > `option`; `group` for optgroups | `aria-selected` on options; `aria-multiselectable` on listbox; `aria-activedescendant` or roving `tabindex` | Arrows; Home/End; Space toggles (multi); type-ahead |
| Modal dialog | `<dialog>` + `showModal()` | `dialog` or `alertdialog` with `aria-modal="true"` | `aria-labelledby` (title) and `aria-describedby`; focus moved into the dialog on open; focus trapped; returned to the trigger on close; background inert | Tab cycles inside; Esc closes |
| Slider | `<input type="range">` | `slider` | `aria-valuenow`, `aria-valuemin`, `aria-valuemax`, `aria-valuetext` (human-readable), `aria-orientation`; name | Arrows ±step; PageUp/PageDown; Home/End |
| Spinbutton | `<input type="number">` | `spinbutton` | `aria-valuenow/min/max`, name | Arrows; Home/End; typing |
| Tree view | — | `tree` > `treeitem` (`group` for children) | `aria-expanded` on parent items; `aria-selected`; `aria-level`/`aria-setsize`/`aria-posinset` when not inferable; roving `tabindex` | Arrows up/down move; Right expands/Left collapses; Home/End; type-ahead |
| Data grid / table | `<table>` with `<th scope>` | `grid` > `row` > `gridcell`/`columnheader`/`rowheader`; `table` for static | `aria-rowcount`/`aria-colcount` when virtualised; `aria-sort` on sortable headers; `aria-selected` | Arrows move between cells; Tab leaves the grid |
| Progress bar | `<progress>` | `progressbar` | `aria-valuenow/min/max` (omit valuenow for indeterminate); name; live-region or `aria-busy` for updates | — (not interactive) |
| Tooltip | `title` (weak) | `tooltip` referenced by `aria-describedby` from the trigger | shown on focus and hover; dismissible (Esc); hoverable; persistent (1.4.13) | Esc closes |
| Status / alert / log live regions | `<output>` (status-like) | `status` (polite), `alert` (assertive), `log` (polite, additive), `marquee`, `timer` | present in DOM before content changes; `aria-atomic`/`aria-relevant` as needed | — |
| Breadcrumb | `<nav aria-label="Breadcrumb"><ol>` | — | `aria-current="page"` on the last item | Tab; Enter |
| Carousel | — | `region` (or `group`) with `aria-roledescription="carousel"`; slides as `group` with `aria-roledescription="slide"` and names ("3 of 8") | rotation controls as buttons with `aria-pressed`/labels; `aria-live="off"` while auto-rotating, `polite` when paused; pause control (2.2.2) | Tab to controls; Enter/Space; Arrows optional |
| Link | `<a href>` | `link` | name from content; `aria-current` where applicable | Enter |
| Custom text input / editor | `<textarea>` / `<input>` | `textbox` (+ `contenteditable`) | name; `aria-multiline`; `aria-invalid`; `aria-describedby`; `aria-required` | typing; standard editing keys |

Every custom interactive element also needs: `tabindex="0"` (or roving `tabindex`) so it is focusable; a visible focus indicator (2.4.7); and state changes reflected in the DOM attributes above *at the moment* the visual state changes.

## Appendix C — ARIA rules of use (informative)

These rules summarise *Using ARIA* (W3C) and the ARIA Authoring Practices; following them avoids most 4.1.2 defects.

1. **First rule: prefer native HTML.** If an HTML element or attribute already provides the semantics and behaviour (`<button>`, `<a href>`, `<input type=…>`, `<select>`, `<details>`, `<dialog>`, `<nav>`, `<main>`, `<table>`), use it instead of re-creating it with ARIA. Native elements give name, role, state, keyboard support and focusability without script.
2. **Do not change native semantics** unless you really must. `<h2 role="tab">`, `<button role="link">`, `<a role="button">` confuse users and tools; wrap or nest instead (`<h2><button>…</button></h2>` for accordions).
3. **All interactive ARIA controls must be keyboard operable.** Adding `role="button"` to a `<div>` does nothing for keyboard users: add `tabindex="0"`, handle Enter and Space, and follow the expected key pattern for the role (see Appendix B). ARIA changes what AT *reports*, never how the element *behaves*.
4. **Do not use `role="presentation"`/`"none"` or `aria-hidden="true"` on focusable elements.** A focusable element hidden from AT is a ghost stop in the tab order; a focusable element with its role removed loses its name and role.
5. **All interactive elements must have an accessible name.** Buttons, links, inputs, custom widgets — a non-empty name via visible text, `<label>`, `alt`, `aria-labelledby` or `aria-label` (in that order of preference), and the visible label text must be contained in the name (2.5.3).
6. **No ARIA is better than bad ARIA.** An invalid role, a misspelled attribute, a state that is never updated or an `aria-labelledby` pointing to a missing ID actively misleads users. Validate ARIA with an automated checker and verify with a screen reader.
7. **Keep states synchronised.** Whenever the visual state changes (open/closed, checked, selected, pressed, current value, busy), update the corresponding `aria-*` attribute in the same code path.
8. **Manage focus deliberately** for composite widgets and dialogs: move focus into dialogs when they open and back to the trigger when they close; use roving `tabindex` or `aria-activedescendant` for composite widgets so there is one tab stop per widget; never let focus land on a hidden element.
9. **Use landmarks and headings for structure, not `role="menu"`.** Site navigation is `<nav>` with lists and links; `menu`/`menubar` roles are for application-style menus with full keyboard semantics.
10. **Live regions must exist before they change**, be used sparingly, and be polite unless the message is urgent (see 4.1.3).
11. **Hide decorative or duplicated content from AT** with `aria-hidden="true"` (non-focusable only) or empty `alt`, and expose icon fonts/SVG that carry meaning with `role="img"` and a name.
12. **Test with real assistive technology** (at least one screen reader in two browsers, plus keyboard-only and, where relevant, voice control). Automated tools catch missing names and invalid ARIA; only AT testing reveals wrong roles, silent state changes and broken focus management.
